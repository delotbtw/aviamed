# Этап 1. Auth, пользователи, регистрация спортсмена

*Спецификация v1.0, 27.10.2026. Опирается на docs/03, 04, 05, 07, 08 и код скелета (коммит 0083ce6). Предположения помечены `ASSUMPTION`, все решения по умолчанию собраны в разделе 9.*

## 1. Цель и границы

**Цель.** Сотрудники и спортсмены могут войти в систему, регистратура регистрирует спортсмена с номером бумажного согласия, админ заводит сотрудников. Все действия этапа попадают в `audit_log`. Это база для этапов с расписанием, делами и осмотрами.

**Входит.** Заглушки 501 в `AuthService` (`refresh`, `logout`, `change_password`) и `UserService` (`create_user`, `register_athlete`, `update_profile`, `deactivate`). Rate limit в `AuthService.login`. Страницы Jinja (раздел 5). Запись в аудит. Команда создания первого админа (раздел 7.1).

**НЕ входит.**
- Справочники и их наполнение (`sports`, `specialties`). Этап использует таблицы как есть; в тестах они заполняются фикстурами.
- Расписание, дела, осмотры, заключения.
- Чтение медданных и аудит чтения (на этапе медданных нет).
- UI журнала аудита, просмотр списка пользователей, реактивация пользователя.
- Восстановление забытого пароля. Сброс делает админ, это отдельная ручка в "Later".
- Редактирование чужих профилей, привязка и смена тренера у существующего спортсмена, OAuth, 2FA.
- Страница редактирования своего профиля (есть только JSON `PATCH /users/me`).

## 2. Пользовательские истории

**Все роли**
- US-1. Войти по email и паролю и попасть в кабинет своей роли.
- US-2. Выйти, чтобы токены перестали работать.
- US-3. Сменить пароль; после смены все мои сессии завершаются.
- US-4. Изменить свой телефон (и ФИО, если роль позволяет) через `PATCH /users/me`.

**Администратор**
- US-5. Создать врача, сотрудника регистратуры, администратора, тренера с профилем и флагом `can_issue_conclusion`.
- US-6. Деактивировать пользователя; он сразу теряет доступ.
- US-7. Зарегистрировать спортсмена (как регистратура).
- US-8. Первый админ создаётся командой при развёртывании.

**Регистратура**
- US-9. При личном визите зарегистрировать спортсмена: аккаунт, профиль, тренер, номер и дата бумажного согласия, одной формой.

**Спортсмен, врач, тренер.** Только US-1..4. Спортсмен не может регистрировать и создавать других.

## 3. Ручки

Общее. Ошибки FastAPI приходят как `{"detail": ...}`. Для всех ручек:
- Без валидного access: 401. Недостаточная роль: 403. Ошибка валидации: 422.
- `email` приводится к нижнему регистру и trim до проверки и сохранения.
- Секреты (пароли, токены, хэши) не попадают в ответы и логи.

### 3.1 POST /auth/login
- **Кто:** все (публичная).
- **Вход:** `LoginRequest {email, password}`. **Выход:** 200 `TokenPair {access_token, refresh_token, token_type="bearer"}`.
- **Ошибки:** 401 `Invalid email or password` (одинаково для: нет пользователя, неверный пароль, `is_active=false`); 429 с заголовком `Retry-After` (секунды), если лимит превышен; 422.
- **Правила:**
  1. Лимит проверяется ДО проверки пароля. Заблокированный аккаунт получает 429 даже с верным паролем.
  2. Счётчики в Redis: по аккаунту (ключ от нормализованного email) и по IP. Неудача увеличивает оба, окно `login_window_s` (900 с) с момента первой неудачи. Порог аккаунта `login_max_attempts` (5): 6-я попытка в окне получает 429. Порог IP: новая настройка `login_max_attempts_ip` = 20.
  3. Успешный вход сбрасывает счётчик аккаунта, но не IP.
  4. Лимит действует и для несуществующих email (счётчик по строке), чтобы не раскрывать существование аккаунта.
  5. Redis недоступен: вход работает без лимита, в лог пишется предупреждение (fail-open). ASSUMPTION.
  6. Успех: refresh-токен в БД (хэш sha256, `expires_at` = now + `refresh_token_ttl_days`, `user_agent` до 255), обновляется `last_login_at`.
  7. IP берётся из `request.client.host`. Заголовок `X-Forwarded-For` не учитываем в MVP.
- **Аудит:** `login_success` (user_id), `login_failed` (user_id, если аккаунт найден, иначе NULL), `login_blocked`. Запись `login_failed` и `login_blocked` должна сохраняться, хотя запрос завершается ошибкой (commit до `raise`). Email в аудит не пишем.

### 3.2 POST /auth/refresh
- **Кто:** все (публичная, нужен refresh-токен). **Вход:** `RefreshRequest {refresh_token}`. **Выход:** 200 новая `TokenPair`.
- **Ошибки:** 401 `Invalid refresh token` (единое сообщение для: неизвестный, истёкший, отозванный, пользователь неактивен); 422.
- **Правила:**
  1. Валидный токен: хэш найден в БД, `revoked_at IS NULL`, `expires_at > now`, нет в Redis blacklist, `user.is_active`.
  2. Ротация: старый токен получает `revoked_at=now` и ключ в Redis `TTL = остаток жизни`; создаётся новый (тот же `user_agent` из запроса).
  3. Предъявлен уже отозванный токен (повторное использование): отозвать ВСЕ активные refresh-токены пользователя, 401, аудит `token_reuse_detected`.
  4. Источник истины это БД. Redis ускоряет проверку; при недоступном Redis проверка идёт только по БД.
  5. Роль в новом access берётся из БД на момент refresh.
- **Аудит:** `token_refresh`.

### 3.3 POST /auth/logout
- **Кто:** все (публичная). **Вход:** `RefreshRequest`. **Выход:** 204.
- **Правила:** отзывает переданный refresh (БД + Redis blacklist). Идемпотентна: неизвестный, чужой или уже отозванный токен тоже даёт 204 без побочных эффектов. Access-токен живёт до истечения (≤15 мин), это принятый компромисс.
- **Аудит:** `logout` только если токен был найден и активен (user_id владельца).

### 3.4 POST /auth/change-password
- **Кто:** любой авторизованный. **Вход:** `ChangePasswordRequest {old_password, new_password}`. **Выход:** 204.
- **Ошибки:** 400 `Invalid old password`; 422 если новый пароль не проходит политику (раздел 7) или совпадает со старым; 401.
- **Правила:** хэш нового пароля через argon2; отзываются все активные refresh-токены пользователя (БД + Redis), включая текущий. Клиент должен войти заново. Проверка старого пароля попадает под тот же лимит попыток аккаунта (счётчик `login`), ASSUMPTION.
- **Аудит:** `password_change`.

### 3.5 GET /users/me
Уже реализована, не меняется. Возвращает `UserRead`. Включена в критерии как регрессия.

### 3.6 PATCH /users/me
- **Кто:** все авторизованные (`Action.PROFILE_EDIT`). **Вход:** `ProfileUpdate` (поля необязательные: `first_name`, `last_name`, `middle_name`, `phone`). **Выход:** 200 `UserRead`.
- **Ошибки:** 403 если спортсмен передал `first_name`, `last_name` или `middle_name`; 422 при пустом теле, неизвестных полях (`email`, `role`, `is_active` и т.п. запрещены, `extra=forbid`), `null` для `first_name`/`last_name`, неверном формате телефона.
- **Правила (матрица прав):** athlete меняет только `phone` ("свои" и ФИО подтверждает регистратура по документам). admin, registrar, doctor, coach меняют `phone` и ФИО. Меняются только переданные поля (`exclude_unset`); `phone=null` очищает телефон; `middle_name=null` очищает отчество.
- **Аудит:** `profile_update` (entity_type `user`, entity_id, без значений).

### 3.7 POST /users (создание сотрудника)
- **Кто:** admin (`Action.USER_CREATE`). **Выход:** 201 `UserRead`.
- **Вход:** `UserCreate` расширяется. Общие: `email`, `password`, `role`, `last_name`, `first_name`, `middle_name?`, `phone?`. По роли:
  - `doctor`: `specialty_id` (обязателен), `cabinet?`, `can_issue_conclusion` (по умолчанию false) → `doctor_profiles`;
  - `registrar`, `admin`: `position?`, `workplace?` → `staff_profiles`;
  - `coach`: `sport_id?` → `coach_profiles`.
- **Ошибки:** 403 не admin; 409 email занят; 422 `role=athlete` (используется `/users/athletes`), поля чужой роли (например, `specialty_id` у registrar), `specialty_id`/`sport_id` не существует, пароль не проходит политику.
- **Правила:** пользователь и профиль создаются в одной транзакции; `is_active=true`. Тренер включён в ручку, иначе привязать `coach_id` невозможно (в матрице создание тренера не описано, см. раздел 9). Один пользователь, одна роль, одна запись профиля.
- **Аудит:** `user_create` (entity user, id нового).

### 3.8 POST /users/athletes (регистрация спортсмена)
- **Кто:** admin, registrar (`Action.ATHLETE_REGISTER`). **Выход:** 201 `UserRead`.
- **Вход:** `AthleteRegister` (как в коде) плюс необязательные `faculty`, `study_group`, `training_stage`, `registry_number`. `health_group` не принимается (его определяет врач).
  Обязательные: `email`, `password`, `last_name`, `first_name`, `birth_date`, `sex`, `consent_paper_number`, `consent_signed_at`.
- **Ошибки:** 403; 409 email занят; 409 номер бумажного согласия уже использован; 422: `birth_date` в будущем или старше 120 лет; `consent_signed_at` в будущем; `consent_paper_number` пустой после trim или длиннее 64; `sport_id` не существует; `coach_id` не указывает на активного пользователя с ролью `coach`; пароль не проходит политику.
- **Правила:**
  1. В одной транзакции: `users(role=athlete)`, `athlete_profiles`, `consents(consent_type="personal_data_health", paper_number, signed_at, created_by=actor)`. Любая ошибка: не создаётся ничего.
  2. Начальный пароль задаёт регистратура и сообщает спортсмену лично.
  3. Номер согласия уникален среди неотозванных согласий этого типа. Сканов нет, только номер и дата.
  4. Ответ не содержит данных о здоровье и профиля тренера.
- **Аудит:** `athlete_register` (entity user, id спортсмена), `consent_create` (entity consent, id согласия).

### 3.9 POST /users/{user_id}/deactivate
- **Кто:** admin. **Выход:** 204.
- **Ошибки:** 403; 404 пользователь не найден; 409 админ пытается деактивировать самого себя.
- **Правила:** `is_active=false`, физического удаления нет. Все активные refresh-токены пользователя отзываются (БД + Redis). Идемпотентна: повторный вызов даёт 204 без повторной записи в аудит. Уже выданный access перестаёт работать немедленно (`get_current_user` проверяет `is_active`). Деактивированный тренер остаётся в `coach_id` спортсменов (обработка в этапе тренера).
- **Аудит:** `user_deactivate` (entity user).

## 4. Аудит: сводка

Запись в `audit_log` делается в транзакции действия (`AuditService.log`), поля `user_id`, `action`, `entity_type`, `entity_id`, `ip`. Для действий без авторизованного пользователя (`login_*`) `user_id` NULL, если аккаунт не определён. Перечень `action`:
`login_success`, `login_failed`, `login_blocked`, `token_refresh`, `token_reuse_detected`, `logout`, `password_change`, `user_create`, `athlete_register`, `consent_create`, `user_deactivate`, `profile_update`.
Значения полей (email, ФИО, телефон, номер согласия, пароли) в аудит не пишутся.

## 5. Страницы (Jinja2 + HTMX + Alpine.js)

Общее: наследуют `base.html`; серверный рендер; HTMX отправляет формы и подставляет ошибки фрагментом; Alpine только для мелочей (показать пароль, блокировка кнопки при отправке). Обработчик `htmx:beforeSwap` в `base.html` разрешает подстановку ответов 4xx. Страницы возвращают реальные HTTP-коды (401/403/409/422/429), не 200 с ошибкой. Все тексты на русском. Страницы вне списка в этапе не создаём.

| URL | Метод | Доступ | Назначение |
|---|---|---|---|
| `/login` | GET | публичный; залогиненного ведёт на `/cabinet` | Форма email и пароль |
| `/login` | POST (форма) | публичный | Проверка, установка cookies, 303 на `next` или `/cabinet`. Ошибка: форма с сообщением "Неверный email или пароль" (401) или "Слишком много попыток, повторите через N мин" (429) |
| `/logout` | POST | авторизованный | Отзыв refresh из cookie, удаление cookies, 303 на `/login` |
| `/cabinet` | GET | любой авторизованный | Главная по роли (ниже) |
| `/cabinet/password` | GET, POST | любой авторизованный | Форма смены пароля (старый, новый, повтор). Успех: cookies удаляются, 303 на `/login` с сообщением "Пароль изменён, войдите заново" |
| `/cabinet/athletes/new` | GET, POST | registrar, admin | Форма регистрации спортсмена (вызывает логику 3.8) |
| `/cabinet/users/new` | GET, POST | admin | Форма создания сотрудника (3.7); поля профиля показываются Alpine в зависимости от выбранной роли |
| `/auth/session` | GET | публичный | Служебный: `?next=/path`. Если в cookie есть годный refresh, ротация, новые cookies и 303 на `next`; иначе 303 на `/login?next=...` |

**Главная `/cabinet` по роли.** Приветствие по ФИО и название роли, ссылки:
- athlete: "Сменить пароль"; блоки "Запись", "Мои осмотры" не показываются до их этапов;
- registrar: "Зарегистрировать спортсмена", "Сменить пароль";
- admin: "Создать пользователя", "Зарегистрировать спортсмена", "Сменить пароль";
- doctor, coach: "Сменить пароль".
Ссылка на недоступную роли страницу не показывается; прямой переход даёт 403 (страница-заглушка, не JSON).

**Правила сессии на страницах.**
- Страницы аутентифицируются по cookie `access_token` (как в `get_current_user`).
- Нет или истёк access на странице (GET): 303 на `/auth/session?next=<текущий путь>`. На HTMX-запросе: 401 с заголовком `HX-Redirect` на тот же адрес.
- `next` принимается только как относительный путь, начинающийся с одного `/` (не `//`, не схема); иначе `/cabinet`.
- После успешной формы создания: фрагмент с сообщением "Создан" и очищенная форма; ошибки валидации показываются под полями.

## 6. Критерии приёмки

Формат: каждый пункт один тест (pytest, интеграционный, реальные PostgreSQL и Redis; Redis допускается заменить fakeredis в модульных). Фикстуры: по одному активному пользователю каждой роли, спортсмен с тренером, справочники `sports`, `specialties`.

**Login и rate limit**
- A-1. Верные данные: 200, оба токена непусты, в `refresh_tokens` строка с хэшем sha256 (raw не хранится), `user_agent` сохранён, `last_login_at` обновлён.
- A-2. Неверный пароль, несуществующий email, неактивный пользователь: все дают 401 с одинаковым `detail`.
- A-3. 5 неудач подряд по одному email: 6-я попытка (даже с верным паролем) даёт 429 и `Retry-After` > 0.
- A-4. Окно истекло (TTL ключа в Redis сброшен): вход снова проходит.
- A-5. Успешный вход сбрасывает счётчик аккаунта (4 неудачи, успех, 4 неудачи: ещё не 429).
- A-6. 20 неудач с одного IP по разным email: следующая попытка с другим email и верным паролем даёт 429.
- A-7. Лимит применяется к несуществующему email так же, как к существующему.
- A-8. Redis недоступен (мок бросает исключение): вход с верным паролем проходит, запрос не падает 500.
- A-9. Аудит: `login_success` с user_id; после неудачного входа есть запись `login_failed` (сохраняется несмотря на 401); при блокировке `login_blocked`; email в таблице аудита не встречается.

**Refresh и logout**
- B-1. Валидный refresh: 200, новая пара; старый хэш получил `revoked_at`, в Redis есть его ключ с TTL > 0 и ≤ остатка жизни; новый хэш добавлен.
- B-2. Повторное использование старого refresh: 401; все остальные токены пользователя отозваны; новый токен из B-1 тоже больше не работает; есть аудит `token_reuse_detected`.
- B-3. Неизвестный, истёкший (`expires_at` в прошлом), отозванный refresh: 401 с единым `detail`.
- B-4. Refresh деактивированного пользователя: 401.
- B-5. Refresh при недоступном Redis: валидный токен проходит, отозванный в БД даёт 401.
- B-6. Роль в новом access равна текущей роли в БД.
- B-7. Logout: 204; токен получает `revoked_at` и ключ в Redis; последующий `/auth/refresh` с ним даёт 401.
- B-8. Logout с неизвестным или уже отозванным токеном: 204, новых записей аудита нет.
- B-9. Access-токен, переданный как refresh (и наоборот: refresh как Bearer): 401.

**Change password**
- C-1. Верный старый и валидный новый: 204; вход со старым паролем 401, с новым 200.
- C-2. Неверный старый: 400, пароль не изменён.
- C-3. Новый совпадает со старым: 422. Новый не проходит политику (короткий, без цифры, без буквы, равен email, длиннее 128): 422 для каждого случая.
- C-4. После смены все refresh-токены пользователя отозваны (БД и Redis); refresh старым токеном даёт 401.
- C-5. Без токена: 401. Есть аудит `password_change`.

**Создание пользователя (POST /users)**
- D-1. Admin создаёт doctor с `specialty_id`, `can_issue_conclusion=true`: 201, в `doctor_profiles` флаг true, `password_hash` начинается с `$argon2`, пароль нигде не возвращается.
- D-2. Без `can_issue_conclusion` у врача флаг false.
- D-3. Создание registrar и admin: 201, есть `staff_profiles` (с `position`, `workplace` или пустой). Создание coach: 201, `coach_profiles`.
- D-4. Врач без `specialty_id`: 422. Несуществующий `specialty_id`: 422, пользователь не создан (транзакция откатилась).
- D-5. `role=athlete`: 422. Поле чужой роли (`specialty_id` у registrar): 422.
- D-6. Email занят (в том числе в другом регистре): 409.
- D-7. Роли registrar, doctor, athlete, coach: 403; без токена 401.
- D-8. Новый пользователь входит с заданным паролем.
- D-9. Аудит `user_create` с id нового пользователя и user_id админа.

**Регистрация спортсмена (POST /users/athletes)**
- E-1. Registrar регистрирует: 201; созданы `users(role=athlete, is_active=true)`, `athlete_profiles` (birth_date, sex, sport_id, coach_id) и `consents` (тип `personal_data_health`, `paper_number`, `signed_at`, `created_by`=registrar).
- E-2. Admin регистрирует спортсмена: 201.
- E-3. Doctor, athlete, coach: 403.
- E-4. Занятый email: 409; номер согласия уже есть у неотозванного согласия: 409; в обоих случаях новых строк в `users`, `athlete_profiles`, `consents` нет.
- E-5. `coach_id` указывает на не-тренера, неактивного или несуществующего: 422. Без `coach_id`: 201, `coach_id` NULL.
- E-6. Несуществующий `sport_id`: 422.
- E-7. `birth_date` в будущем: 422. `consent_signed_at` в будущем: 422. Пустой или из пробелов `consent_paper_number`: 422.
- E-8. Передан `health_group`: игнорируется или 422 (по `extra=forbid`: 422); в профиле NULL.

**Страницы**

- H-3. `POST /login` неверные: 401, HTML содержит "Неверный email или пароль", cookies не установлены. После лимита: 429 и текст про повтор.

## 7. Нефункциональные требования

**Пароли**
- argon2 (`PasswordHasher` из `app/core/security.py`), параметры по умолчанию библиотеки.
- Политика: 10..128 символов, минимум одна буква и одна цифра, не равен email. Применяется при создании пользователя, регистрации спортсмена, смене пароля. Единое место валидации (общий валидатор схем).
- Пароль не логируется и не возвращается ни в каком ответе.

**Токены**
- Access: JWT HS256, TTL `access_token_ttl_min` (15 мин), claims `sub`, `role`, `type=access`, `iat`, `exp`.
- Refresh: случайный `secrets.token_urlsafe(48)`, в БД только sha256, TTL `refresh_token_ttl_days` (7 дней).
- Ротация при каждом refresh. Повторное использование отозванного токена отзывает все токены пользователя.
- Redis blacklist: ключ от хэша токена, TTL = остаток жизни токена. Источник истины БД.
- `secret_key` не равен значению по умолчанию вне `debug`: при старте с `change-me` и `debug=false` приложение не запускается. ASSUMPTION.

**Cookies (веб-страницы)**
- `access_token`: HttpOnly, SameSite=Lax, Path=/, `Max-Age` = TTL access, `Secure` при `debug=false`.
- `refresh_token`: HttpOnly, SameSite=Lax, Path=/auth, `Max-Age` = TTL refresh, `Secure` при `debug=false`.
- JSON-ручки `/auth/*` токены в cookie не ставят.
- CSRF: SameSite=Lax плюс проверка `Origin` для небезопасных методов при аутентификации по cookie.

**Лимиты.** Аккаунт 5 попыток за 900 с, IP 20 попыток за 900 с (настройки `login_max_attempts`, `login_window_s`, `login_max_attempts_ip`). Лимит Nginx вне объёма этого этапа. Значения уточняются нагрузочными тестами.

**Прочее**
- Нет раскрытия существования аккаунтов: одинаковые сообщения и (по возможности) близкое время ответа при отсутствующем пользователе (хэш-заглушка для выравнивания времени). ASSUMPTION.
- Все многошаговые операции (создание пользователя с профилем, регистрация спортсмена, отзыв токенов при деактивации) атомарны.
- Пользователей не удаляем.
- Логи без ПДн (email, ФИО, телефон маскируются или не пишутся).
- Изменения схемы: только Alembic. Для этапа схема БД не меняется (все таблицы есть); если понадобится индекс на `consents(consent_type, paper_number)`, добавляется миграцией.
- Данные для тестов только синтетические.

### 10.1 Уникальный индекс номера бумажного согласия (миграция)

**Зачем.** Сейчас уникальность `paper_number` среди неотозванных согласий проверяется запросом `paper_number_taken` без блокировки. Две параллельные регистрации с одним номером обе пройдут проверку и создадут дубль. По принципу проекта (как с `appointments.slot_id`) такой инвариант должен гарантироваться БД, а приложение лишь отдаёт понятное сообщение.

**Что сделать.**
- Новая миграция Alembic (отдельная ревизия поверх `378a416b2f4b`): частичный уникальный индекс на `consents(consent_type, paper_number)` с условием `revoked_at IS NULL`; описать его и в модели (`Index(..., unique=True, postgresql_where=...)`), чтобы `alembic check` оставался чистым.
- В `AthleteRegistrationService` перехватывать `IntegrityError` по этому индексу и переводить в доменное исключение «номер согласия уже использован» (409), как сейчас делает проверка запросом; проверку запросом оставить для понятного сообщения в обычном случае.
- Тест гонки: две параллельные регистрации с одним номером → ровно одна успешна, вторая 409, в `consents` одна запись.
- Проверить `alembic upgrade head`, `downgrade -1`, `alembic check`.

- Redis в тестах эмулируется fakeredis: достаточно для MVP.

## 11. Транзакции и конкурентность

**Принципы.**
- Каждая бизнес-операция это одна транзакция: все записи (пользователь, профиль, согласие, токены, аудит) коммитятся или откатываются вместе (`UnitOfWork.commit()` один раз в конце). Исключение: записи аудита неудачного входа и блокировки коммитятся до `raise`, это намеренно (раздел 3.1).
- Защита от гонок только на уровне строк и ограничений БД: `SELECT ... FOR UPDATE` по конкретным строкам, уникальные индексы, атомарные `UPDATE`/`INCR`. Табличных блокировок, `LOCK TABLE` и `SERIALIZABLE` нет.
- Единый порядок захвата блокировок: строка `users` → строки `refresh_tokens` (в `login`, `refresh`, `logout`, `change_password`, `deactivate`, ветка reuse). Строка `users` берётся как `FOR NO KEY UPDATE` (`get_for_update`): писатели по-прежнему сериализуются, но блокировка не конфликтует с `FOR KEY SHARE`, который внешние ключи (в том числе `audit_log.user_id`) берут на ту же строку. Иначе два админа, деактивирующие друг друга (A→B, B→A, A→B→C→A), встречались бы в дедлоке через собственные вставки аудита. Argon2 (хэш, проверка) и вызовы Redis выполняются до захвата блокировок или после коммита (в `login` освобождение счётчиков в Redis идёт после `commit`; blacklist обновляется после коммита, best effort, БД источник истины). У клиента Redis заданы `socket_timeout` и `socket_connect_timeout` по 1 с, зависший Redis не держит запросы.
- Чтение-изменение-запись без блокировки или версии нет: `update_profile` пишет только изменённые колонки одной строки `users` (`UPDATE ... SET` по затронутым полям), конфликт одного поля решается "последняя запись побеждает", что приемлемо для профиля. Для дел (`medical_cases`) уже есть `version_id_col` (оптимистичная блокировка), для слотов и записей `UniqueConstraint`, это будет использовать этап расписания.
