# 09. Тестирование

*Черновик v0.1, 26.10.2026.*

## 1. Виды тестов

| Вид | Что проверяет | Инструмент |
|---|---|---|
| Модульные | Бизнес-правила сервисного слоя (переходы статусов, проверка допуска) | pytest |
| Интеграционные | Ручки вместе с реальной БД: права по ролям, запись на слот, выдача заключения | pytest-asyncio, тестовая PostgreSQL в docker-compose |
| Нагрузочные | Предел сервера, узкие места | Locust |
| Сценарный прогон | Полный путь спортсмена на тестовых данных вместе с директором медцентра | Вручную |

## 2. Интеграционные тесты

- Отдельная тестовая БД в docker-compose, пересоздаётся перед прогоном.
- Обязательные проверки:
  - матрица прав: каждая роль получает отказ там, где доступа быть не должно (особенно тренер и регистратура к результатам осмотров);
  - допустимые и недопустимые переходы статусов;
  - невозможность двойной записи на один слот;
  - невозможность выдать заключение, пока не закрыты обязательные осмотры;
  - срабатывание ограничения попыток входа;
  - запись в журнал при чтении и изменении медданных.

## 3. Нагрузочное тестирование

### Где и как

- **На сервере**, максимально близком к целевому (те же vCPU и память, что у VPS за ~1000 ₽ в месяц), в отдельном окружении (staging): своя БД с синтетическими данными, не боевая.
- **Генератор нагрузки запускается с другой машины**, иначе он съест ресурсы сервера и исказит результат.
- На время теста IP генератора добавляется в белый список ограничения запросов Nginx; иначе измерим работу Nginx, а не приложения.
- Если сервера под тест ещё нет, арендуем VPS на несколько дней.
- Структура: отдельная папка `loadtests/` в репозитории со своим Dockerfile или compose.

### Сценарии

1. Вход в систему.
2. Запись на слот (проверяет гонки: много пользователей на ограниченное число слотов).
3. Выдача PDF заключения.

### Что измеряем

Число запросов в секунду, время ответа (медиана и p95), долю ошибок, загрузку CPU и памяти, использование пула соединений PostgreSQL.

### Что фиксируем в отчёте

Конфигурацию сервера (vCPU, ОЗУ), число воркеров приложения, размер пула соединений, версию приложения, объём тестовых данных.

### Ожидание

**Генерация PDF, скорее всего, определит предел сервера**, потому что рендер нагружает процессор. Измеряем её отдельно, настраиваем жёсткий лимит на ручку PDF и оцениваем необходимость очереди.

## 4. Сценарный прогон

Проводится с директором медцентра на условных спортсменах и тестовых данных, без реальных пользователей и без замеров времени. Итог — письменный отзыв директора. Подготовить: набор тестовых спортсменов, расписание слотов, сценарий «регистрация → запись → осмотры → нагрузочный тест → заключение → PDF».

## 5. Решения

- Инструмент выбран: Locust (сценарии пишутся на Python).
- Конфигурация сервера для замеров (ориентир: 2 vCPU, 2–4 ГБ ОЗУ).
